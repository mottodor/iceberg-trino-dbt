## 1. Цель и ожидаемый результат

### Задано источником

Независимый учебный проект должен обеспечить глубокое изучение аналитического моделирования поверх Apache Iceberg. Основной фокус:

- устройство Iceberg: data files, metadata files, manifests и snapshots;
- работа с Iceberg tables через REST catalog;
- Trino SQL;
- dbt-модели Bronze/Silver/Gold;
- typed Silver state;
- Kimball facts и dimensions;
- SCD Type 2;
- schema evolution и historical queries через snapshot/time travel;
- dbt tests и custom reconciliation tests;
- осознанное применение incremental predicates;
- выбор partitioning по паттернам запросов, анализ `EXPLAIN` и file pruning;
- диагностика small-files problem;
- безопасные snapshot expiration и compaction как отдельное упражнение.

Источники данных поступают как готовые deterministic fixtures. Ingestion, CDC и orchestration не должны отвлекать от lakehouse-задач.

### Решено пользователем

Выбран единый бизнес-домен **логистики**. Главный аналитический результат — анализ **сроков доставки и эффективности маршрутов**.

### Состояние готовности

Основные контракты, deterministic fixture package и проверяемые результаты первого среза согласованы, реализованы и подтверждены acceptance evidence проекта. Контракты core vertical slice заморожены и не изменяются новым срезом. Schema evolution детализирован как следующий изолированный учебный срез; его DDL и проверки на этапе Specify не выполнялись.

## 5. Существенные контракты поведения и данных

Для домена логистики согласовано:

- основная единица учёта — посылка (`package_id`);
- одно отправление может включать несколько независимо доставляемых посылок;
- изменения представлены неизменяемыми tracking-событиями;
- событие сообщает статус посылки, место и бизнес-время события;
- базовый жизненный цикл включает `created`, `picked_up`, `arrived_at_hub`, `departed_hub`, `out_for_delivery`, `delivered`;
- Bronze сохраняет все события, Silver строит текущее typed state посылки;
- срок доставки равен `delivered_at − picked_up_at`;
- опоздание равно `max(delivered_at − promised_delivery_at, 0)`;
- доставка считается выполненной вовремя, если `delivered_at <= promised_delivery_at`;
- временная эффективность сопоставляет фактическую и плановую продолжительность;
- хабы и tracking-события содержат координаты;
- плановый и фактический маршруты сравниваются по расстояниям, вычисленным из координат, а не по готовым итоговым дистанциям во входе;
- плановая дистанция — сумма геодезических расстояний между последовательными плановыми контрольными точками;
- фактическая дистанция — сумма геодезических расстояний между всеми последовательными tracking-событиями с координатами, упорядоченными по бизнес-времени;
- расстояние между двумя точками вычисляется в Trino через `ST_Distance` над `SphericalGeography`: `ST_Point(longitude, latitude)` преобразуется функцией `to_spherical_geography`; результат измеряется в метрах;
- абсолютное отклонение маршрута равно `actual_distance − planned_distance`;
- процентное отклонение при ненулевой плановой дистанции равно `(actual_distance − planned_distance) / planned_distance × 100%`;
- время ожидания в хабе определяется интервалом между парными событиями `arrived_at_hub` и `departed_hub` для одного посещения посылкой одного хаба;
- показатели по хабам должны позволять выявить узлы, в которых формируется задержка внутри общего срока доставки;
- каждое событие содержит `event_id`, `package_id`, `event_at` и `received_at`;
- Bronze сохраняет каждую исходную строку вместе с идентификатором fixture/batch;
- Silver оставляет одну каноническую запись на `event_id`; точные повторы не попадают в канонический набор;
- один `event_id` с различающимися payload считается ошибкой качества и должен приводить к провалу соответствующей проверки;
- позднее событие принимается и занимает место по `event_at`, независимо от порядка загрузки;
- при одинаковом `event_at` детерминированный порядок задаётся `received_at`, затем `event_id`;
- текущее состояние посылки определяется максимальным каноническим событием по `(event_at, received_at, event_id)`;
- после позднего события пересчитываются зависящие от него состояние и метрики соответствующей посылки;
- план маршрута является SCD2-измерением со стабильным `route_id` и версионными строками;
- версия плана содержит контрольные точки, плановую продолжительность, SLA, `valid_from`, `valid_to` и признак текущей версии;
- изменение контрольных точек, плановой продолжительности или SLA закрывает предыдущую и создаёт новую версию;
- интервалы версий одного `route_id` не пересекаются;
- факт доставки связывается с версией маршрута, для которой `valid_from <= picked_up_at < valid_to`; для открытой текущей версии верхняя граница отсутствует;
- `promised_delivery_at = picked_up_at + sla_duration` связанной версии маршрута;
- Gold-факт доставки имеет grain «одна строка на посылку после первого `picked_up`» и обновляется как accumulating snapshot;
- milestone timestamps заполняются по мере появления соответствующих событий;
- для недоставленной посылки `delivered_at`, итоговая продолжительность, итоговое опоздание и `is_on_time` равны `NULL`;
- для недоставленной посылки пройденная дистанция и завершённые посещения хабов рассчитываются по доступным каноническим событиям;
- после `delivered` та же строка получает финальные метрики, новая строка для завершения не создаётся;
- каждое `arrived_at_hub` открывает посещение хаба с отдельным `visit_seq`;
- ближайшее следующее `departed_at_hub` той же посылки и того же хаба закрывает открытое посещение;
- повторный приезд в тот же хаб создаёт новое посещение, а не расширяет старое;
- открытое посещение без `departed_at_hub` допустимо для посылки в пути и имеет `dwell_time = NULL`;
- `departed_at_hub` без открытого прибытия и второе прибытие в тот же хаб до закрытия текущего посещения считаются ошибками качества.

Все три направления анализа дополняют друг друга: итоговый SLA показывает результат, ожидание в хабах локализует временные потери, а сравнение маршрутов показывает пространственное отклонение.

### Согласованный deterministic fixture package первого среза

Предложение использует координаты на экваторе, чтобы отношения расстояний имели независимо выводимые ожидаемые значения и не зависели от выбранного радиуса Земли.

#### Хабы и точки

| Код | Longitude | Latitude | Роль |
|---|---:|---:|---|
| `A` | 0.0 | 0.0 | отправной хаб |
| `X` | 0.5 | 0.0 | отклонение маршрута |
| `B` | 1.0 | 0.0 | хаб версии 1 и фактического отклонения |
| `D` | 1.5 | 0.0 | хаб версии 2 |
| `C` | 2.0 | 0.0 | конечный хаб |

#### Версии плана `R1`

| Версия | Период действия | План | SLA |
|---|---|---|---:|
| `R1-V1` | `[2025-01-01T00:00Z, 2025-02-01T00:00Z)` | `A → B → C` | 48 часов |
| `R1-V2` | `[2025-02-01T00:00Z, ∞)` | `A → D → C` | 36 часов |

Обе версии имеют плановую длину, равную двум градусам дуги экватора. Это не фиксированное число метров в спецификации; проверяется отношение вычисленных дистанций.

Использует `R1-V2`; срок 48 ч при SLA 36 ч; опоздание 12 ч; маршрут `A → B → X → D → C` имеет длину 150% плана; отклонение +50%; суммарный dwell = 16 ч, максимум в `X`. |
| `P3` | `S2` | Точный дубль и поздние события | `picked_up=2025-02-10T09:00Z`, `delivered=2025-02-11T21:00Z`; позднее загружаются завершённые посещения `B` 2 ч и `X` 1 ч с бизнес-временем до доставки, а также точный дубль события `picked_up`. После второй загрузки текущее состояние остаётся `delivered`, срок и on-time не меняются, canonical event count не увеличивается из-за дубля, маршрут становится `A → B → X → C` и равен 150% плана. |

`P2` и `P3` принадлежат одному shipment `S2` и должны сохранять независимые состояния и метрики.

#### Отрицательные DQ-сценарии

Они не входят в успешный baseline-run и выполняются отдельно:

- одинаковый `event_id` с различающимся payload должен провалить DQ-проверку;
- `departed_at_hub` без открытого `arrived_at_hub` должен провалить DQ-проверку;
- второе `arrived_at_hub` для той же посылки и хаба до закрытия текущего посещения должно провалить DQ-проверку.

### Делегировано или отложено

- Полный физический формат fixture-файлов, имена полей сверх согласованного контракта и структура каталогов выбираются агентом при реализации.
- События с разными `event_id` считаются разными событиями; невозможная последовательность выявляется DQ-тестами. Более сложная semantic deduplication не входит в первый срез.
- Gold первого среза ограничен accumulating package fact, hub-visit fact и агрегатом эффективности по версии маршрута.
- Поздно обнаруженная ретроактивная корректировка плана маршрута не входит в первый срез и должна быть определена перед соответствующим расширением.
- Точный сценарий schema evolution определён и одобрен в разделе 8.
- Отдельный time travel slice, partitioning benchmark и maintenance по-прежнему отложены и не отменены.

### AC-015 — metadata-only schema evolution

- **Действие:** последовательно переименовать колонку, расширить числовой тип и добавить nullable-колонку согласно DEC-030.

### AC-017 — writer compatibility и создание snapshot S1

- **Исходные условия:** действует новая схема, current snapshot всё ещё `S0`.
- **Действие:** сначала попытаться выполнить `INSERT` с явным списком колонок, содержащим старое имя `delivery_status`; затем выполнить корректный `INSERT` строки `EVO-P5` с актуальными именами и типами.
- **Ожидаемый результат:** запись со старым именем завершается ошибкой и не создаёт snapshot; корректная запись добавляет ровно одну строку и создаёт новый snapshot `S1`, для которого `parent_id = S0`.

### AC-018 — совместимость S0 и S1

- **Исходные условия:** доступны snapshot IDs `S0` и `S1`; snapshot expiration не выполнялся. Trino 484 разрешает колонки historical query по схеме выбранного snapshot, поэтому S0 использует schema 0, а S1/current — текущую schema 3.
- **Действие:** выполнить три явные snapshot-schema-aware проекции, нормализованные к одному семиколоночному контракту. Для `S0` выбрать legacy-колонки, задать `CAST(NULL AS VARCHAR) AS delivery_priority`, переименовать `delivery_status AS current_status` и расширить `completed_visit_count` до `BIGINT`; для `S1` и current использовать актуальные имена и типы. `SELECT *` запрещён.
- **Ожидаемый результат:** нормализованный `S0` возвращает только `P1`–`P4`, сохраняя статусы и counts, с `delivery_priority=NULL`; `S1` и текущая таблица возвращают те же четыре строки плюс `EVO-P5` с `delivery_priority='express'`; результаты `S1` и current совпадают точно, а все три result set имеют одинаковые имена, порядок и типы колонок.
- **Способ проверки:** три отсортированных typed result set, exact expected-row assertions и machine comparison нормализованного S1 с current; `typeof(...)` подтверждает типы `VARCHAR, VARCHAR, VARCHAR, VARCHAR, BIGINT, DOUBLE, BOOLEAN`, а отдельные `IS NULL` assertions отличают SQL NULL от строкового литерала. Snapshot IDs берутся из `$snapshots`, а не хардкодятся; command evidence фиксирует historical/current имена.
- **Основание:** DEC-030–DEC-032; наблюдаемое поведение Trino 484 Iceberg `FOR VERSION AS OF`; пользовательское решение по OPEN-021.

### AC-019 — запрет сужения типа и атомарность ошибки

- **Исходные условия:** текущая схема содержит `completed_visit_count BIGINT`, current snapshot равен `S1`.
- **Действие:** попытаться выполнить `ALTER COLUMN completed_visit_count SET DATA TYPE INTEGER`.
- **Ожидаемый результат:** Trino отклоняет narrowing conversion; схема остаётся `BIGINT`; current snapshot остаётся `S1`; число строк и data-file paths не меняются.
- **Способ проверки:** ожидаемый non-zero exit status, повторный `DESCRIBE`, `$snapshots`, count и file-path comparison.
- **Основание:** DEC-030, DEC-033; Trino Iceberg widening-only type evolution.

### AC-020 — сквозное доказательство schema evolution slice

- **Исходные условия:** core baseline и evolution exercise выполняются в чистом изолированном run prefix.
- **Действие:** выполнить порядок из раздела 8, сохранить результаты запросов, schema/snapshot metadata и object-storage evidence, затем повторить core regression.
- **Ожидаемый результат:** AC-013–AC-019 проходят; Polaris продолжает регистрировать одну evolution-таблицу; object storage содержит data и metadata Iceberg-объекты; негативные операции не оставляют частичных изменений; task-owned schema и объекты удаляются без snapshot expiration или compaction.
- **Способ проверки:** автоматизированный acceptance workflow с именованными проверками, evidence manifest и безопасным cleanup; это план проверки, а не уже выполненный результат.
- **Основание:** `docs/idea.md`, DEC-028–DEC-033.

## 7. Первый законченный срез

### Решено пользователем: core vertical slice

Первый срез включает:

- рабочую цепочку S3-compatible storage → Polaris → Iceberg → Trino → dbt;
- deterministic fixture batches для tracking-событий и версий плана маршрута;
- immutable Bronze;
- Silver с каноническими событиями и текущим состоянием посылки;
- SCD2-измерение плана маршрута с join по `picked_up_at`;
- Gold-результаты по SLA доставки, времени в хабах и отклонению фактического маршрута;
- dbt tests и reconciliation для ключевых контрактов данных.

Core vertical slice завершён. Его контракты, fixtures и критерии AC-003–AC-012 остаются утверждённой неизменной базой.

В последующие срезы после schema evolution отложены, но остаются обязательной частью полного scope:

- отдельное упражнение time travel;
- partitioning benchmark и анализ `EXPLAIN`/file pruning;
- small-files diagnostics;
- snapshot expiration и compaction.

## 8. Следующий законченный срез: schema evolution

### 8.1. Статус и учебные цели

Раздел одобрен пользователем как контракт следующего среза. Он не изменяет утверждённую core-часть.

После завершения среза обучающийся должен уметь:

- объяснить, почему Iceberg связывает колонки по field ID, а не по физической позиции;
- различать изменение table metadata/schema ID и создание нового data snapshot;
- выполнить через Trino безопасные `RENAME COLUMN`, widening type update и `ADD COLUMN`;
- показать, что schema evolution не требует переписывания существующих Parquet-файлов;
- объяснить reader compatibility: current table читает старые data files через новую схему, а новая nullable-колонка даёт `NULL` для старых строк; historical query в Trino 484 разрешает колонки по схеме выбранного snapshot и требует явной нормализации контракта;
- объяснить writer compatibility: после rename запись должна использовать актуальное имя, а narrowing type change отклоняется;
- сопоставить schema, snapshots, data files и metadata files по фактическим запросам и object-storage evidence.

### 8.4. Изменения схемы

Операции выполняются строго последовательно:

```sql
ALTER TABLE <evolution_table>
RENAME COLUMN delivery_status TO current_status;

ALTER TABLE <evolution_table>
ALTER COLUMN completed_visit_count SET DATA TYPE BIGINT;

ALTER TABLE <evolution_table>
ADD COLUMN delivery_priority VARCHAR AFTER route_version_id;
```

Ожидаемая текущая схема после DDL:

| Позиция | Колонка | Тип | Совместимость |
|---:|---|---|---|
| 1 | `package_id` | `VARCHAR` | без изменения |
| 2 | `route_version_id` | `VARCHAR` | без изменения |
| 3 | `delivery_priority` | `VARCHAR` | новая nullable-колонка; старые строки читаются как `NULL` |
| 4 | `current_status` | `VARCHAR` | то же field ID и те же значения, что у `delivery_status` |
| 5 | `completed_visit_count` | `BIGINT` | widening из `INTEGER`; значения не меняются |
| 6 | `delivery_duration_hours` | `DOUBLE` | без изменения |
| 7 | `is_on_time` | `BOOLEAN` | без изменения |

После каждого DDL проверяется, что current snapshot по-прежнему равен `S0`, а Parquet data-file paths, sizes и checksums не изменились. В metadata JSON `delivery_status → current_status` сохраняет field ID, `completed_visit_count` сохраняет field ID при смене типа, а `delivery_priority` получает новый ранее не использованный field ID. `current-schema-id` должен измениться относительно S0. Новые Iceberg metadata files допустимы и ожидаемы; новые data snapshots и Parquet files до записи `EVO-P5` недопустимы.

### 8.5. Порядок запусков

1. Запустить полный утверждённый core baseline и сохранить core regression evidence.

3. Сохранить `DESCRIBE`, строки S0, `$snapshots` и data-file/object listing.
4. Выполнить три DDL из раздела 8.4 по одному, после каждого проверяя schema и отсутствие нового snapshot/data-file rewrite.
5. Выполнить чтение `P1`–`P4` через новую схему и подтвердить `delivery_priority IS NULL`.
6. Запустить негативный `INSERT` со старым именем `delivery_status`; подтвердить ошибку и неизменность `S0`.
7. Запустить негативное сужение `BIGINT → INTEGER`; подтвердить ошибку и неизменность schema/snapshot/files.
8. Выполнить корректный `INSERT` строки `EVO-P5` по новой схеме и зафиксировать новый snapshot как `S1`.
9. Выполнить historical/current queries для `S0`, `S1` и current table.

### 8.8. Негативные сценарии

Каждый сценарий запускается отдельно с фиксацией состояния до и после. Ошибка считается ожидаемой только при non-zero status и сохранении schema/data invariants.

1. **Старое имя колонки после rename**
   - действие: `INSERT` с явной колонкой `delivery_status`;
   - ожидание: column-resolution error; строка не добавлена; snapshot не создан; имя не действует как alias.
2. **Narrowing type evolution**
   - действие: `ALTER COLUMN completed_visit_count SET DATA TYPE INTEGER` после успешного widening;
   - ожидание: unsupported type change; колонка остаётся `BIGINT`; snapshot, rows и files не меняются.
3. **Защита core boundary**
   - действие: сравнить core schemas и baseline outputs после упражнения;
   - ожидание: любое изменение core contract считается провалом среза, даже если evolution-таблица сама прошла проверки.

Точный текст сообщений Trino не является контрактом; проверяются класс операции, non-zero status и отсутствие частичных изменений.

### 8.9. Что исключено из этого среза

- изменение схем Bronze/Silver/Gold или raw fixture tables;
- добавление `delivery_priority` в core analytics;
- `DROP COLUMN`, nested-field evolution и произвольная перестановка существующих полей;
- изменение partition spec — это partitioning slice;
- полноценное исследование timestamp-based time travel, branches, tags и rollback — это отдельный time travel slice;
- snapshot expiration, orphan-file cleanup, compaction и small-files remediation;
- проверка совместимости несколькими query engines;
- performance benchmark и изменение incremental strategy dbt-моделей.

Использование `FOR VERSION AS OF` здесь ограничено доказательством совместимости до/после schema evolution и не заменяет отдельный time travel slice.

## 11. Черновик следующего среза: partitioning и file-pruning benchmark

### 11.1. Статус, источник и границы

**Статус раздела:** `APPROVED`

**Используемый skill:** Specify `0.2.0`

**Утверждённая база:** разделы 1–10 этого документа, включая завершённые core vertical slice и schema evolution slice.

**Текущая роль раздела:** накопление решений для следующего изолированного среза; реализация, сервисы и технические эксперименты в Specify не выполняются.

Завершённые контракты, fixtures, модели, ожидаемые результаты и критерии AC-003–AC-020 не изменяются. Новый срез не должен добавлять benchmark-строки в core Bronze/Silver/Gold или в schema-evolution таблицу.

В срез входят выбор partition spec под смешанный workload, анализ `EXPLAIN`, доказательство partition/file pruning и сравнение физически разных Iceberg-таблиц с логически одинаковыми данными. Sorting/clustering, small-files remediation, compaction, snapshot expiration и изменение incremental strategy не входят в этот срез.

### 11.2. Решения пользователя, уже принятые для среза

1. Benchmark использует отдельный детерминированный синтетический набор в логистическом домене, а не текущие четыре core package-факта.
2. Синтетические данные создаются непосредственно как изолированный benchmark fact с grain «одна строка на синтетическую посылку». Отдельный Bronze/Silver/Gold pipeline для benchmark не создаётся.
3. Основное временное измерение — pickup cohort по `picked_up_at`; `picked_up_at` заполнен у каждой benchmark-строки.
4. Workload смешанный и включает временной предикат, маршрутный предикат, их комбинацию и полный scan без partition-фильтра.
5. Сравниваются четыре физических layout одного логического dataset:
   - unpartitioned control;
   - `day(picked_up_at)`;
   - `bucket(route_id, 4)`;
   - `day(picked_up_at)` вместе с `bucket(route_id, 4)`.
6. Используются два логических распределения — balanced и skewed. Каждое записывается во все четыре layout; всего восемь benchmark-таблиц.
7. Balanced и skewed имеют одинаковые схему, общий объём, временной диапазон и набор маршрутов. Меняется только плотность строк по датам и маршрутам.
8. Фиксированный объём каждого логического dataset:
   - 50 последовательных pickup-дней;
   - 10 маршрутов;
   - 256 000 строк;
   - balanced содержит 512 строк на каждую комбинацию `день × маршрут`.
   Суммарно восемь физических таблиц содержат 2 048 000 строк.
9. Skew выраженный и действует независимо по обоим измерениям:
   - 20% маршрутов содержат 80% строк;
   - 20% дней содержат 80% строк;
   - hot + peak содержит 64%, cold + peak — 16%, hot + off-peak — 16%, cold + off-peak — 4% строк;
   - размеры одной комбинации соответственно равны 8192, 512, 512 и 32 строкам.
10. Два hot routes должны попадать в разные из четырёх buckets; все четыре buckets должны быть непустыми. Фактическое отображение фиксированных `route_id` проверяется через Trino `system.bucket`, а не предполагается по имени.
11. Обязательные запросы возвращают одну агрегированную строку с точными метриками:
    - `package_count`;
    - `completed_count`;
    - `on_time_count`;
    - `total_delay_minutes`.
12. Completed/on-time/delay определяются одной детерминированной формулой для всех групп и не зависят от hot/cold или peak/off-peak. Skew влияет только на число строк.
13. Главный критерий эффективности — структурное доказательство pruning, а не wall-clock latency. Время выполнения может сохраняться как диагностическая метрика, но не определяет PASS/FAIL.
14. Benchmark должен изолировать partition pruning: намеренная сортировка по `picked_up_at`/`route_id` запрещена, а unpartitioned data files должны перекрывать широкий диапазон дат и маршрутов. Случайно кластеризованный control не считается валидной базой.
15. Evidence contract включает:
    - точный набор подходящих partition tuples по `$partitions`;
    - выбранные data files, record counts и file sizes по `$files`;
    - partition constraints в `EXPLAIN`;
    - physical input в `EXPLAIN ANALYZE`;
    - точное равенство query results между layout;
    - относительное уменьшение physical input для подходящего layout против control;
    - отсутствие pruning для полного scan.
    Точное равенство physical input сумме Parquet file sizes не требуется из-за column projection, encoding и compression.
16. Регрессия завершённых slices выполняется по impact-based правилу. Их артефакты являются immutable boundary; при отсутствии изменений общих компонентов достаточно path-scoped diff/fingerprint checks и runtime isolation. Если меняется Compose, infra, общий helper или иной shared path, полный acceptance затронутого завершённого slice становится обязательным.

### 11.3. Обязательная форма workload

Выбран минимальный полный набор из 13 query cases. Каждый case выполняется против всех четырёх layout соответствующего dataset с одинаковой проекцией агрегатов.

Balanced содержит четыре case:

1. один representative pickup-day;
2. один representative route;
3. комбинация этого дня и маршрута;
4. full scan без partition-предиката.

Skewed содержит девять case:

1. peak day;
2. off-peak day;
3. hot route;
4. cold route;
5. hot route + peak day;
6. hot route + off-peak day;
7. cold route + peak day;
8. cold route + off-peak day;
9. full scan.

Всего выполняются 52 логических query-layout сравнения, не считая отдельных `EXPLAIN`/`EXPLAIN ANALYZE` evidence-команд. Balanced не повторяет симметричные дни и маршруты.

Фиксированный pickup-range охватывает 50 UTC-дней с 2025-03-01 по 2025-04-19 включительно. Peak period — первые десять дней, с 2025-03-01 по 2025-03-10. Representative peak day — 2025-03-05, representative off-peak day — 2025-03-30; balanced использует 2025-03-30.

Дневные predicates задаются полуинтервалом по исходной timestamp-колонке, например `picked_up_at >= TIMESTAMP '2025-03-30 00:00:00 UTC' AND picked_up_at < TIMESTAMP '2025-03-31 00:00:00 UTC'`. `CAST(picked_up_at AS DATE)` и иные query-side преобразования partition-колонки в обязательном workload не используются.

Route IDs выбираются детерминированно из последовательности `BENCH-R0001`, `BENCH-R0002`, … по `system.bucket(route_id, 4)`. Итоговое распределение route IDs по buckets равно 3/3/2/2: buckets 0 и 1 содержат по одному hot и двум cold routes, buckets 2 и 3 — по два cold routes. Representative hot route — hot route из bucket 0; representative cold route — первый cold route из bucket 2. Balanced использует тот же representative cold route. Конкретный полученный mapping сохраняется как evidence.

### 11.4. Детерминированный контракт состояний

Completed/on-time/delay задаются циклом длиной 16 внутри каждой комбинации `pickup-day × route`. Локальная позиция строки в комбинации принимает значения от 0 до `group_size - 1`; правило использует `position % 16`.

| Позиции modulo 16 | Состояние | `delivered_at` | `is_on_time` | `delay_minutes` |
| --- | --- | --- | --- | ---: |
| 0–1 | active | `NULL` | `NULL` | `NULL` |
| 2–11 | completed on time | не `NULL` | `true` | 0 |
| 12 | completed late | не `NULL` | `false` | 30 |
| 13 | completed late | не `NULL` | `false` | 60 |
| 14 | completed late | не `NULL` | `false` | 90 |
| 15 | completed late | не `NULL` | `false` | 120 |

На каждые 16 строк ожидаются `package_count=16`, `completed_count=14`, `on_time_count=10` и `total_delay_minutes=300`. Все размеры групп 32, 512 и 8192 делятся на 16, поэтому правило даёт точные агрегаты для любого полного day/route segment без floating-point допусков.

Typed-схема benchmark fact:

| Колонка | Тип | Правило |
| --- | --- | --- |
| `package_id` | `VARCHAR` | Уникальный детерминированный ID внутри balanced или skewed dataset; одинаков для четырёх layout одного dataset. |
| `route_id` | `VARCHAR` | Один из 10 bucket-aware маршрутов. |
| `route_version_id` | `VARCHAR` | `<route_id>-V1`. |
| `picked_up_at` | `TIMESTAMP(6) WITH TIME ZONE` | UTC day start плюс `position % 1440` минут. |
| `promised_delivery_at` | `TIMESTAMP(6) WITH TIME ZONE` | `picked_up_at + INTERVAL '48' HOUR`. |
| `delivered_at` | `TIMESTAMP(6) WITH TIME ZONE` | `NULL` для active; обещанный срок для on-time; обещанный срок плюс задержка для late. |
| `is_on_time` | `BOOLEAN` | `NULL` для active; иначе результат `delivered_at <= promised_delivery_at`. |
| `delay_minutes` | `BIGINT` | `NULL` для active; 0 для on-time; 30, 60, 90 или 120 для late. |

Общий SLA benchmark равен 48 часам. Он используется только внутри benchmark slice и не меняет SLA core fixtures. Для completed on-time `delivered_at=promised_delivery_at`; для late `delivered_at=promised_delivery_at + delay_minutes`. Дополнительные shipment, hub, distance или payload-колонки в обязательную схему не входят.

### 11.6. File-topology contract

File topology фиксируется инвариантами результата, а не точным числом writer output files:

- каждая из восьми таблиц содержит ровно 256 000 строк;
- layout `D` содержит ровно 50 непустых day partition tuples;
- layout `R` содержит ровно 4 непустых bucket tuples;
- layout `DR` содержит ровно 200 непустых day+bucket tuples;
- каждый partition tuple содержит хотя бы один data file;
- фактические partition specs подтверждаются table metadata/`SHOW CREATE TABLE`, а record/file counts и sizes — `$partitions` и `$files`;
- перед benchmark file-level lower/upper bounds проверяются для representative predicates: внутри уже выбранных partition tuples bounds не должны давать дополнительное исключение файлов, которое подменяет partition-pruning evidence;
- намеренная сортировка, `sorted_by`, compaction и повторная запись ради оптимизации bounds запрещены.

Точное число files и их individual sizes не являются контрактом, поскольку зависят от Trino writer parallelism и target file size. Write batching и interleaving делегированы реализации только в пределах достижения перечисленных инвариантов без изменения строк, partition specs и workload. Если topology gate не выполнен, benchmark не получает PASS. Допускается предварительный технический probe write protocol на следующем этапе; его результат не вправе ослабить контракт.

### 11.7. Критерии приёмки partitioning/file-pruning slice

#### AC-021 — неизменность завершённых slices и runtime-изоляция

- **Исходные условия:** core vertical slice и schema evolution slice утверждены и завершены; их артефакты определены текущими разделами 1–10.
- **Действие:** реализовать и выполнить partition benchmark в отдельном task-owned run prefix.
- **Ожидаемый результат:** benchmark не меняет core/schema-evolution fixtures, модели, таблицы и ожидаемые результаты; не записывает строки в их schemas/object prefixes; все новые таблицы находятся только в task-owned benchmark schema. Если затронут shared path, повторяется acceptance соответствующего завершённого slice.
- **Способ проверки:** path-scoped diff/fingerprint check, catalog/schema/object listing до и после benchmark, а при shared change — сохранённый PASS затронутого acceptance workflow.
- **Основание:** прямое решение пользователя не изменять контракты завершённых slices; раздел 11.1 и impact-based boundary.

#### AC-022 — детерминированные balanced и skewed facts

- **Исходные условия:** доступны pinned Trino/Iceberg stack и чистый task-owned benchmark schema.
- **Действие:** создать balanced и skewed datasets по разделам 11.2–11.4.
- **Ожидаемый результат:** каждый dataset содержит ровно 256 000 уникальных package rows, 50 UTC pickup-days, 10 routes и typed-схему из восьми колонок. Balanced содержит 512 rows на каждый day-route; skewed содержит 8192/512/512/32 rows для hot+peak/cold+peak/hot+off-peak/cold+off-peak. State cycle даёт точные full-scan агрегаты 256 000/224 000/160 000/4 800 000.
- **Способ проверки:** `DESCRIBE`, uniqueness/not-null assertions, exact grouped counts по day/route/class, exact full-scan aggregate и проверка timestamp/SLA/state formulas.
- **Основание:** решения пользователя о размере, skew, схеме и 16-строчном цикле.

#### AC-023 — восемь физических layout и их логическая эквивалентность

- **Исходные условия:** оба логических dataset проходят AC-022.
- **Действие:** записать каждый dataset в `U`, `D`, `R` и `DR` layout.
- **Ожидаемый результат:** существуют ровно восемь task-owned benchmark tables; `U` не partitioned, `D` использует `day(picked_up_at)`, `R` — `bucket(route_id, 4)`, `DR` — оба transforms. Все четыре layout одного dataset содержат идентичные строки; все buckets непусты, hot routes находятся в разных buckets; topology равна 50 tuples для `D`, 4 для `R` и 200 для `DR`, каждый tuple имеет data file.
- **Способ проверки:** `SHOW CREATE TABLE`/table metadata, `system.bucket`, `$partitions`, `$files`, exact row counts, bidirectional set difference или эквивалентная full-row reconciliation между layout.
- **Основание:** разделы 11.2 и 11.6.

#### AC-024 — balanced workload и pruning

- **Исходные условия:** balanced `U`/`D`/`R`/`DR` проходят AC-023 и topology/bounds gate.
- **Действие:** выполнить четыре balanced cases из раздела 11.3 против всех layout.
- **Ожидаемый результат:** агрегаты точно совпадают с balanced-таблицей раздела 11.5. Eligible records соответствуют matrix: day 256000/5120/256000/5120; route 256000/256000/51200/51200; day+route 256000/5120/51200/1024; full scan 256000 для всех. Подходящие `D`, `R` и `DR` показывают меньший physical input относительно `U`; `DR` для combined predicate выбирает строгий subset относительно отдельно `D` и `R`.
- **Способ проверки:** exact result comparison, `$partitions`/`$files`, `EXPLAIN`, `EXPLAIN ANALYZE` и machine-readable comparison evidence.
- **Основание:** согласованные exact expectations раздела 11.5.

#### AC-025 — skewed workload и влияние плотности

- **Исходные условия:** skewed `U`/`D`/`R`/`DR` проходят AC-023 и topology/bounds gate.
- **Действие:** выполнить девять skewed cases из раздела 11.3 против всех layout.
- **Ожидаемый результат:** агрегаты точно совпадают со skewed-таблицей раздела 11.5. Eligible records равны 20480/1280 для peak/off-peak day в `D`/`DR`, 115200/12800 для hot/cold route bucket в `R`/`DR` и 9216/576/1024/64 для четырёх combined cases в `DR`. Evidence показывает, что одинаковый тип pruning может читать разный объём из-за skew, а bucket pruning оставляет строки других routes того же bucket.
- **Способ проверки:** exact result comparison, partition/file metadata, plans, physical input и сопоставление hot/cold/peak/off-peak cases.
- **Основание:** решения пользователя о выраженном независимом skew и exact expectations раздела 11.5.

#### AC-026 — причинность и полнота pruning evidence

- **Исходные условия:** восемь таблиц созданы, но benchmark queries ещё не признаны валидными.
- **Действие:** выполнить topology/bounds preflight и собрать evidence каждого case.
- **Ожидаемый результат:** file bounds не дают дополнительного исключения, подменяющего partition pruning; для каждого case сохранены SQL, exact result, partition/file candidates, `EXPLAIN` и `EXPLAIN ANALYZE`; full scan выбирает все tuples/files и не заявляется как pruning. Wall-clock time не влияет на PASS/FAIL.
- **Способ проверки:** автоматическая полнота evidence matrix 13 cases × 4 layout, bounds assertions, отсутствие пустых test sets и проверка обязательных scan statistics.
- **Основание:** выбранный структурный evidence contract и file-topology contract.

#### AC-027 — end-to-end регистрация, cleanup и воспроизводимость

- **Исходные условия:** AC-021–AC-026 прошли в уникальном run prefix.
- **Действие:** сохранить catalog/object evidence, затем удалить только task-owned benchmark schema и остановить только запущенные workflow services согласно исходному состоянию среды.
- **Ожидаемый результат:** до cleanup Polaris/Trino регистрируют восемь benchmark tables, RustFS содержит их Iceberg data/metadata objects; после cleanup отсутствуют task-owned schema и object prefix, pre-existing volumes сохранены, compaction/snapshot expiration/orphan cleanup не выполнялись. Summary получает PASS только после evidence completeness и cleanup checks.
- **Способ проверки:** catalog/table listing, bounded object listing, command log, acceptance summary, evidence manifest, secret scan и post-cleanup environment assertions.
- **Основание:** изоляция среза, существующий безопасный lifecycle pattern проекта и явные исключения раздела 11.1.

### 11.8. Документированные технические основания

Это позволяет отличить развитие данных от восстановления в истории одного объекта. Имена, схема и технический порядок определены ниже; они не меняют согласованных бизнес-правил.

Не входят в текущую детализацию: новые бизнес-правила логистики, изменение согласованных fixtures, partitioning benchmark, schema evolution, snapshot expiration, orphan-file cleanup, compaction и small-files remediation. Branches/tags могут рассматриваться отдельно, но не являются условием PASS этого среза.

### 12.3. Цель и смысл результата

Обучающийся должен воспроизвести разные сохранённые состояния одной Iceberg-таблицы и отличить два действия:

- historical query читает выбранное прошлое состояние, не меняя текущее;
- rollback меняет состояние, которое возвращает обычный запрос к таблице; он не означает отмену бизнес-события или удаление исходной истории tracking-событий.

Commit time — момент изменения состояния Iceberg-таблицы, а `event_at` — бизнес-время логистического события. Поздно загруженное событие с ранним `event_at` не должно автоматически появляться в snapshot, созданном до его записи.

**Согласованный смысл последовательности:**

1. `H0` — учебная копия результата до поздних событий P3.
2. `H1` — результат после корректной обработки поздних событий. Historical queries сравнивают `H0`/`H1`, не меняя current.
3. `Hbad` — намеренно испорченная запись только в учебной таблице, после `H1`.
4. Rollback выполняется к `H1`, а не к `H0`: корректные поздние события и зависящие от них метрики сохраняются в восстановленном current.

`H0`, `H1`, `Hbad` — символические имена состояний, не фиксированные snapshot IDs. Сохранение чтения `Hbad` по его snapshot ID после rollback согласовано как отдельная проверка: ошибочное состояние перестаёт быть current, но остаётся доступным для расследования без удаления snapshots/files. Это ожидаемый контракт, не результат запуска.

**Согласованный сценарий, не новые core fixtures:** учебная таблица содержит проекцию всех четырёх посылок P1–P4. У P1/P2/P4 значения во всех состояниях неизменны. Для P3 согласованы следующие результаты:

| Показатель P3 | H0 | H1 | Hbad | Current после rollback к H1 |
| --- | --- | --- | --- | --- |
| `current_status` | `delivered` | `delivered` | `delivered` | `delivered` |
| `delivery_duration_hours` | 36 | 36 | **360 — намеренная ошибка** | 36 |
| `is_on_time` | true | true | true | true |
| Завершённые посещения | 0 | 2 | 2 | 2 |
| Завершённый dwell, часы | 0 | 3 | 3 | 3 |
| Actual/planned distance | 1.0 | 1.5 | 1.5 | 1.5 |

Корректные значения выводятся из уже утверждённых событий и правил P3 в разделе 5 и AC-005: доставка длится 36 часов; поздние визиты дают 2 + 1 = 3 часа dwell и маршрут 150% плана. Изменение `36 → 360` не следует из событий и согласовано только как fault injection. Оно намеренно делает duration несогласованной с исходными событиями; другие показатели не пересчитываются и бизнес-правила не меняются. Эталон проверки не должен вычисляться из испорченной строки.

### 12.4. Таблица, входы и независимые ожидания

Учебная таблица: `<catalog>.<run_prefix>_time_travel.time_travel_package_delivery`. Она не является dbt-моделью core и не заменяется при повторных core builds. Схема постоянна во всех snapshots:

| Колонка | Тип | Источник / смысл |
| --- | --- | --- |
| `package_id` | `VARCHAR` | Core Gold, уникальная посылка. |
| `route_version_id` | `VARCHAR` | Core Gold, согласованная SCD2-привязка. |
| `current_status` | `VARCHAR` | Core Gold. |
| `delivery_duration_hours` | `DOUBLE` | Core Gold; только в Hbad у P3 намеренно равно 360. |
| `is_on_time` | `BOOLEAN` | Core Gold; NULL для P4. |
| `completed_visit_count` | `BIGINT` | Число закрытых посещений из core Gold. |
| `completed_dwell_hours` | `DOUBLE` | Завершённый dwell из core Gold с явным приведением типа. |
| `actual_to_planned_ratio` | `DOUBLE` | `actual_distance_meters / planned_distance_meters`, без бизнес-округления. Это отношение доступной дистанции, не nullable final deviation. |

Данные получаются из неизменённых baseline fixtures и моделей, запущенных в новых task-owned source schemas: сначала только batch_1, затем batch_2. Использовать результаты заранее завершённого полного baseline вместо реального состояния до batch_2 нельзя. Нельзя хардкодить H0/H1 как единственный источник фактических строк: таблица должна получать проекцию реальных staged Gold results.

Независимый эталон H0 выводится из раздела 5 и baseline fixtures:

| package_id | route_version_id | current_status | duration, ч | is_on_time | closed visits | dwell, ч | actual/planned |
| --- | --- | --- | ---: | --- | ---: | ---: | ---: |
| P1 | R1-V1 | delivered | 48 | true | 1 | 4 | 1.0 |
| P2 | R1-V2 | delivered | 48 | false | 3 | 16 | 1.5 |
| P3 | R1-V2 | delivered | 36 | true | 0 | 0 | 1.0 |
| P4 | R1-V2 | arrived_at_hub | NULL | NULL | 0 | 0 | 0.75 |

H1 отличается только тремя значениями P3: `completed_visit_count=2`, `completed_dwell_hours=3`, `actual_to_planned_ratio=1.5`. Hbad отличается от H1 только `P3.delivery_duration_hours=360`. После rollback current должен совпадать с H1. Во всех состояниях ровно четыре уникальных package rows, без EVO-P5 и benchmark rows.

Для P4 отношение 0.75 выводится из доступного маршрута A → D длиной 1.5 градуса против двух градусов планового A → D → C. Это не финальная метрика завершённой доставки; duration/on-time P4 остаются SQL NULL.

Строки сравниваются в порядке `package_id` с проверкой типов и SQL NULL, а не строкового литерала `'NULL'`. Counts, статусы, boolean и часы сравниваются точно; отношение дистанций с независимыми числами 1.0/1.5/0.75 — с допуском 0.0001, соответствующим DEC-024 (0.01 процентного пункта). Current и historical reads одного snapshot дополнительно должны совпадать точно между собой. Expected values не генерируются проверяемой Gold SQL-логикой и не копируются из результата под тестом: основание — приведённые таблицы, исходные координаты и временные интервалы.

### 12.5. Порядок, snapshots и timestamp boundaries

1. Зафиксировать исходное состояние среды, immutable fingerprints и разрешённые task-owned schemas/object prefixes; убедиться, что run prefix новый и пустой.
2. Загрузить только batch_1 в изолированные source schemas и выполнить неизменённые core-модели. Проверить исходную проекцию по эталону H0; создать учебную таблицу одним data commit и сохранить H0.
3. Загрузить batch_2, перестроить source Gold и проверить проекцию H1. Единственной data-операцией обновить три изменившихся показателя P3 в учебной таблице из проверенного Gold. Сохранить H1; H1.parent_id = H0.
4. Одной операцией намеренно изменить только duration P3 с 36 до 360; сохранить Hbad, Hbad.parent_id = H1. До rollback current = Hbad, но source Gold остаётся корректным H1.
5. Выполнить snapshot-ID queries для H0/H1/Hbad и все timestamp-проверки ниже; подтвердить, что чтения не меняют Hbad/current и metadata state.
6. Выполнить негативные проверки чтения и rollback на отсутствующий ID; после каждой подтвердить отсутствие частичных изменений.
7. Выполнить `ALTER TABLE <time_travel_table> EXECUTE rollback_to_snapshot(<H1>)`. Проверить current = H1, повторить snapshot-ID queries для H0/H1/Hbad, сохранить metadata/file evidence.
8. Выполнить оставшиеся regression/isolation checks, сохранить итоговые evidence, удалить только task-owned ресурсы и восстановить исходное состояние среды.

Создание H0 и переходы H1/Hbad дают ровно три data snapshots одной и той же таблицы. Нельзя заменять её через DROP/CREATE, CTAS replacement или dbt table materialization между состояниями. Число и размеры writer files не фиксируются; data/delete files при UPDATE могут изменяться согласно механизму записи Trino. Schema evolution и изменение partition spec не выполняются.

Snapshot IDs извлекаются из фактических metadata, не хардкодятся и не сортируются численно. Для определения current используется `current-snapshot-id` актуального Iceberg metadata JSON, сверенный с history; максимальный `committed_at` из `$snapshots` **не** является способом определения current после rollback.

**Timestamp contract до rollback:** обозначим моменты первого становления H0/H1/Hbad текущими как `t0`, `t1`, `tb`. Они берутся из `$history.made_current_at`, сверяются с `$snapshots.committed_at` и сохраняются в UTC без потери миллисекунд. Обязателен строгий порядок `t0 < t1 < tb` с промежутками, допускающими хотя бы одну внутреннюю миллисекундную точку между соседними commits. Реализация обеспечивает разделение записей и проверяет его по metadata; одинаковые времена не разрешается произвольно упорядочивать по snapshot ID.

| Момент запроса `FOR TIMESTAMP AS OF` | Ожидаемый result set |
| --- | --- |
| `t0` | H0 |
| Любая одна зафиксированная точка строго между t0 и t1 | H0 |
| `t1` | H1 |
| Любая одна зафиксированная точка строго между t1 и tb | H1 |
| `tb` | Hbad |
| `t0 - 1 миллисекунда` | Ошибка отсутствия snapshot на этот момент, без fallback. |

Выбирается последнее сохранённое состояние на момент `<=` указанного timestamp; это не фильтр по `event_at`. Для объяснения различия дополнительно сохраняются исходные P3-E05–P3-E08: event_at соответственно 2025-02-10 15:00/17:00 UTC и 2025-02-11 10:00/11:00 UTC, received_at — 2025-02-12 09:00–09:03 UTC. Они произошли до доставки P3, но их влияние появляется в учебной таблице только в H1, после фактической записи. SQL timestamp-запросов использует явную временную зону UTC; fixture dates не подставляются вместо commit timestamps.

Timestamp-запросы после rollback не входят в обязательный scope TT-1: неоднозначность выбора по повторному становлению snapshot текущим не подменяется предположением. После rollback обязательны current и сохранённые snapshot-ID reads. Это не исключает timestamp time travel из среза — он полностью проверяется на линейной истории до rollback.

### 12.6. Rollback, негативные операции и metadata/file invariants

Успешный rollback к H1 должен менять current pointer, но не создавать четвёртый data snapshot и не уничтожать Hbad. После него:

- current-snapshot-id = H1; набор `$snapshots` по-прежнему H0/H1/Hbad, их IDs и parent links неизменны;
- `$history` содержит последовательность смен current H0 → H1 → Hbad → H1; последнее становление H1 имеет более поздний `made_current_at`, чем первоначальное. Не следует требовать совпадения его original `committed_at` со временем rollback;
- H0/H1 являются current ancestors, Hbad — нет; snapshot Hbad остаётся доступным по ID;
- схема и schema ID не меняются; data/delete файлы, существовавшие непосредственно перед rollback, сохраняют пути, размеры и checksums, новых data/delete файлов rollback не создаёт;
- допускаются новые metadata JSON и изменение catalog metadata pointer; текущий `$files` отражает H1 и поэтому не обязан совпадать с текущим `$files` Hbad;
- current rows совпадают с H1; source Gold и все не принадлежащие задаче объекты не меняются.

Checksums относятся к фактическому содержимому или надёжной object checksum; S3 multipart ETag нельзя без проверки объявлять MD5. Полный bounded object inventory дополняет `$files`, поскольку current `$files` не перечисляет все исторические и delete files.

Обязательные негативные операции:

1. Historical read с положительным BIGINT snapshot ID, отсутствие которого предварительно подтверждено в metadata учебной таблицы.
2. Historical read на `t0 - 1 миллисекунда`.
3. `rollback_to_snapshot` с тем же заведомо отсутствующим ID, пока current = Hbad.

Каждая операция требует non-zero status и содержательной диагностики недоступной версии/момента, а не произвольного сбоя подключения или синтаксиса. Точный текст сообщения не фиксируется. До и после сравниваются current ID, schema, rows, snapshots/history, catalog metadata location и task object inventory: ошибочная операция не должна делать commit, создавать/удалять файлы или менять указатели. Нельзя удалять существующий snapshot ради получения негативного входа. Ошибочное значение 360 — **успешная намеренная запись**, а не ожидаемый SQL failure: обнаруживается сравнением с эталоном, а не требованием падения существующего core dbt test.

### 12.7. Изоляция и regression

- Все source fixture/Bronze/Silver/Gold schemas и учебная schema имеют уникальный task-owned prefix. Их точный allowlist и object locations сохраняются до первой записи. Source core-модели читаются/выполняются без редактирования.
- Source builds не выполняются в заранее существующих пользовательских schemas. Новая Hbad-запись допустима только в учебной таблице, не в source Gold или fixtures.
- Path-scoped fingerprints защищают `dbt/`, прежние acceptance runners и их специализированные helpers, `compose.yaml`, `docker/`, `infra/` и другие shared components. Изменения ограничиваются новыми Time travel artifacts и дополнением раздела 12; README/status могут обновляться на следующем этапе только без изменения завершённых контрактов.
- Если shared code/config не менялись, достаточно immutable path checks и runtime isolation; полный повтор всех старых acceptance не требуется. Выполнение staged core source builds и финального baseline dbt build остаётся обязательным входом нового exercise.
- Если изменён общий helper, Compose, infra или иной shared component, требуется PASS полного acceptance каждого затронутого завершённого среза; непроверенное влияние не разрешает пропускать regression. Менять их бизнес-правила, fixtures или старые критерии нельзя даже при успешном запуске.
- До/после проверяются listings и metadata pointers не принадлежащих задаче project tables; object listings ограничены проектным bucket и разрешёнными prefixes, не сканируют посторонние пользовательские хранилища. Заранее существующие тома сохраняются.

### 12.8. Evidence, cleanup и воспроизводимость

Workflow использует новый run ID и сохраняет evidence под `artifacts/acceptance/<run-id>/`: summary с результатами AC, команды/exit codes, SQL и typed result sets, expected comparisons, соответствие H0/H1/Hbad реальным IDs и UTC timestamps, schemas, `$snapshots`, `$history`, актуальные metadata JSON, bounded catalog/object inventories и file checksum evidence до/после rollback.

Сохраняются evidence manifest и secret scan по образцу проекта; credentials, tokens и содержимое локального `.env` не должны попадать в evidence. Полные historical expected sets не заменяются одной проверкой count или сравнением двух одинаково ошибочных запросов.

После проверок удаляются только task-owned source schemas, учебная schema и их object prefixes; подтверждается отсутствие оставшихся task-owned объектов, включая файлы Hbad, не входящие в restored current. Это финальное удаление временного exercise, а не snapshot maintenance: `expire_snapshots`, orphan cleanup и compaction не выполняются. Остальные tables/prefixes/volumes сохраняются. Исходно работающий stack остаётся работающим; исходно остановленный возвращается в остановленное состояние; разрешённые изменения lifecycle заранее фиксируются. Cleanup предпринимается и при ошибке; ошибка cleanup отражается в summary и исключает PASS. Итоговый PASS допустим только после полноты evidence, regression/isolation и успешной проверки cleanup.

### 12.9. Критерии приёмки Time travel slice

#### AC-028 — неизменность завершённых срезов

- **Исходные условия:** утверждены и завершены core, schema evolution, partitioning/file-pruning; сохранены fingerprints, исходные listings и metadata pointers.
- **Действие:** выполнить новый exercise по разделам 12.4–12.8.
- **Ожидаемый результат:** fixtures, модели, контракты AC-003–AC-027 и пользовательские tables/prefixes не изменены; Hbad существует только в новой учебной таблице. Shared changes сопровождаются обязательным PASS затронутой regression.
- **Способ проверки:** path-scoped diff/fingerprints, runtime allowlist, catalog/object comparisons и impact-based acceptance evidence.
- **Основание:** DEC-034, DEC-040.

#### AC-029 — historical query и commit time

- **Вход:** H0/H1/Hbad с независимо заданными строками раздела 12.4 и разделёнными UTC commit times t0/t1/tb.
- **Действие:** до rollback прочитать все три snapshot IDs и выполнить пять успешных timestamp cases раздела 12.5; сопоставить с event_at/received_at поздних событий P3.
- **Ожидаемый результат:** все result sets имеют восемь заданных типов и четыре уникальных package rows, соответствуют выбранному состоянию; H0 не содержит эффекта поздних событий, H1 содержит; Hbad отличается только duration P3. Current остаётся Hbad, metadata и files от чтений не меняются.
- **Способ проверки:** independent expected-row assertions с указанными допусками и NULL/type checks, snapshot/time mapping, сравнение current и metadata до/после чтений.
- **Основание:** DEC-035, DEC-037–DEC-039; AC-005 и согласованные числа P3.

#### AC-030 — rollback и сохранённая история

- **Вход:** current = Hbad, H1 — его прямой предок; сохранён полный file/metadata inventory.
- **Действие:** rollback к H1, затем чтения current и H0/H1/Hbad по snapshot IDs.
- **Ожидаемый результат:** current = H1, duration P3 снова 36, visits/dwell/ratio сохраняют 2/3/1.5; P1/P2/P4 неизменны. Все три historical состояния читаемы. Новый data snapshot и новые data/delete files не создаются, старые сохраняются; history и metadata соответствуют разделу 12.6.
- **Способ проверки:** expected rows и точное current-vs-H1 comparison, current-snapshot-id, `$snapshots`/`$history`, schema IDs, file path/size/checksum comparison и object listing.
- **Основание:** DEC-037–DEC-039, явное одобрение сохранения Hbad пользователем.

#### AC-031 — атомарные негативные операции

- **Вход:** current = Hbad; выбран отсутствующий snapshot ID и момент t0 минус одна миллисекунда.
- **Действие:** выполнить два ошибочных чтения и ошибочный rollback из раздела 12.6.
- **Ожидаемый результат:** каждая операция завершается ожидаемой содержательной ошибкой, без fallback, commit, изменения current/rows/schema/history/metadata pointer или object inventory.
- **Способ проверки:** non-zero status, класс диагностической ошибки и полное before/after comparison по каждой операции.
- **Основание:** DEC-035; контракт негативных операций раздела 12.6.

#### AC-032 — staged источник и независимый эталон

- **Вход:** неизменённые baseline batch_1/batch_2 и core-модели в новых source schemas.
- **Действие:** получить H0 из первого staged Gold, затем H1 из Gold после batch_2; выполнить fault injection только в учебную таблицу.
- **Ожидаемый результат:** оба корректных состояния получены реальным выполнением моделей и совпадают с независимо выведенными строками; повторный Gold build не уничтожает учебную историю. Финальный полный baseline dbt build проходит, source Gold остаётся корректным H1 при Hbad в учебной таблице.
- **Способ проверки:** staged command evidence и source queries, exact projection assertions, baseline dbt build result; числа эталона трассируются к разделу 5, fixtures и таблице 12.4, а не к output SQL под тестом.
- **Основание:** DEC-037–DEC-038, требования к источнику и эталону раздела 12.4.

#### AC-033 — end-to-end evidence, cleanup и среда

- **Исходные условия:** уникальный run ID, pinned stack; все записи ограничены task allowlist.
- **Действие:** выполнить exercise, сохранить catalog/storage/query evidence, затем cleanup и восстановление среды.
- **Ожидаемый результат:** Polaris/Trino регистрируют учебную таблицу, RustFS хранит Iceberg data/metadata; AC-028–AC-032 проходят; evidence полон и не содержит секретов. После cleanup task schemas и все их objects отсутствуют, pre-existing tables/volumes сохранены, lifecycle среды восстановлен. Maintenance не выполнялся.
- **Способ проверки:** acceptance summary, manifest, secret scan, command logs, bounded post-cleanup listings и environment assertions. Summary PASS только после всех gates.
- **Основание:** DEC-034, DEC-040; раздел 12.8.

### 12.10. Документация, неизвестные и готовность передачи

Проверена официальная документация **Trino 484**, Context7 `/trinodb/trino/484`, первоисточник: <https://github.com/trinodb/trino/blob/484/docs/src/main/sphinx/connector/iceberg.md>.

Она документирует `FOR VERSION AS OF`, `FOR TIMESTAMP AS OF` с выбором последнего snapshot до или на указанный момент, `ALTER TABLE … EXECUTE rollback_to_snapshot(…)`, `$snapshots` и `$history`. Последняя выводится из snapshot log, а один snapshot может появиться несколько раз при повторном становлении current. Различие `made_current_at` и `committed_at` особенно существенно для rollback. Release notes 484 отдельно фиксируют исправление `$history`: <https://github.com/trinodb/trino/blob/484/docs/src/main/sphinx/release/release-484.md>.

Документированный механизм не является runtime PASS. Создание snapshots через UPDATE, rollback с сохранением исторических файлов, негативные операции и cleanup на pinned Trino–Polaris–RustFS stack ещё не выполнялись в рамках этого среза. Их наблюдаемый результат должен удовлетворить AC; неудача проверки не разрешает молча ослаблять контракт.
