## 1. Цель и ожидаемый результат

### Задано источником

Независимый учебный проект должен обеспечить глубокое изучение аналитического моделирования поверх Apache Iceberg. Основной фокус:

- устройство Iceberg: data files, metadata files, manifests и snapshots;
- работа с Iceberg tables через REST catalog;
- Trino SQL;
- dbt-модели Bronze/Silver/Gold;
- typed Silver state;
- Kimball facts и dimensions;
- SCD Type 2;
- schema evolution и historical queries через snapshot/time travel;
- dbt tests и custom reconciliation tests;
- осознанное применение incremental predicates;
- выбор partitioning по паттернам запросов, анализ `EXPLAIN` и file pruning;
- диагностика small-files problem;
- безопасные snapshot expiration и compaction как отдельное упражнение.

Источники данных поступают как готовые deterministic fixtures. Ingestion, CDC и orchestration не должны отвлекать от lakehouse-задач.

### Решено пользователем

Выбран единый бизнес-домен **логистики**. Главный аналитический результат — анализ **сроков доставки и эффективности маршрутов**.

### Состояние готовности

Основные контракты, deterministic fixture package и проверяемые результаты первого среза согласованы. Решения для последующих срезов, не влияющие на контракты core vertical slice, явно отложены. Реальное выполнение стека и тестов на этапе Specify не проводилось.

## 5. Существенные контракты поведения и данных

Для домена логистики согласовано:

- основная единица учёта — посылка (`package_id`);
- одно отправление может включать несколько независимо доставляемых посылок;
- изменения представлены неизменяемыми tracking-событиями;
- событие сообщает статус посылки, место и бизнес-время события;
- базовый жизненный цикл включает `created`, `picked_up`, `arrived_at_hub`, `departed_hub`, `out_for_delivery`, `delivered`;
- Bronze сохраняет все события, Silver строит текущее typed state посылки;
- срок доставки равен `delivered_at − picked_up_at`;
- опоздание равно `max(delivered_at − promised_delivery_at, 0)`;
- доставка считается выполненной вовремя, если `delivered_at <= promised_delivery_at`;
- временная эффективность сопоставляет фактическую и плановую продолжительность;
- хабы и tracking-события содержат координаты;
- плановый и фактический маршруты сравниваются по расстояниям, вычисленным из координат, а не по готовым итоговым дистанциям во входе;
- плановая дистанция — сумма геодезических расстояний между последовательными плановыми контрольными точками;
- фактическая дистанция — сумма геодезических расстояний между всеми последовательными tracking-событиями с координатами, упорядоченными по бизнес-времени;
- расстояние между двумя точками вычисляется в Trino через `ST_Distance` над `SphericalGeography`: `ST_Point(longitude, latitude)` преобразуется функцией `to_spherical_geography`; результат измеряется в метрах;
- абсолютное отклонение маршрута равно `actual_distance − planned_distance`;
- процентное отклонение при ненулевой плановой дистанции равно `(actual_distance − planned_distance) / planned_distance × 100%`;
- время ожидания в хабе определяется интервалом между парными событиями `arrived_at_hub` и `departed_hub` для одного посещения посылкой одного хаба;
- показатели по хабам должны позволять выявить узлы, в которых формируется задержка внутри общего срока доставки;
- каждое событие содержит `event_id`, `package_id`, `event_at` и `received_at`;
- Bronze сохраняет каждую исходную строку вместе с идентификатором fixture/batch;
- Silver оставляет одну каноническую запись на `event_id`; точные повторы не попадают в канонический набор;
- один `event_id` с различающимися payload считается ошибкой качества и должен приводить к провалу соответствующей проверки;
- позднее событие принимается и занимает место по `event_at`, независимо от порядка загрузки;
- при одинаковом `event_at` детерминированный порядок задаётся `received_at`, затем `event_id`;
- текущее состояние посылки определяется максимальным каноническим событием по `(event_at, received_at, event_id)`;
- после позднего события пересчитываются зависящие от него состояние и метрики соответствующей посылки;
- план маршрута является SCD2-измерением со стабильным `route_id` и версионными строками;
- версия плана содержит контрольные точки, плановую продолжительность, SLA, `valid_from`, `valid_to` и признак текущей версии;
- изменение контрольных точек, плановой продолжительности или SLA закрывает предыдущую и создаёт новую версию;
- интервалы версий одного `route_id` не пересекаются;
- факт доставки связывается с версией маршрута, для которой `valid_from <= picked_up_at < valid_to`; для открытой текущей версии верхняя граница отсутствует;
- `promised_delivery_at = picked_up_at + sla_duration` связанной версии маршрута;
- Gold-факт доставки имеет grain «одна строка на посылку после первого `picked_up`» и обновляется как accumulating snapshot;
- milestone timestamps заполняются по мере появления соответствующих событий;
- для недоставленной посылки `delivered_at`, итоговая продолжительность, итоговое опоздание и `is_on_time` равны `NULL`;
- для недоставленной посылки пройденная дистанция и завершённые посещения хабов рассчитываются по доступным каноническим событиям;
- после `delivered` та же строка получает финальные метрики, новая строка для завершения не создаётся;
- каждое `arrived_at_hub` открывает посещение хаба с отдельным `visit_seq`;
- ближайшее следующее `departed_at_hub` той же посылки и того же хаба закрывает открытое посещение;
- повторный приезд в тот же хаб создаёт новое посещение, а не расширяет старое;
- открытое посещение без `departed_at_hub` допустимо для посылки в пути и имеет `dwell_time = NULL`;
- `departed_at_hub` без открытого прибытия и второе прибытие в тот же хаб до закрытия текущего посещения считаются ошибками качества.

Все три направления анализа дополняют друг друга: итоговый SLA показывает результат, ожидание в хабах локализует временные потери, а сравнение маршрутов показывает пространственное отклонение.

### Согласованный deterministic fixture package первого среза

Предложение использует координаты на экваторе, чтобы отношения расстояний имели независимо выводимые ожидаемые значения и не зависели от выбранного радиуса Земли.

#### Хабы и точки

| Код | Longitude | Latitude | Роль |
|---|---:|---:|---|
| `A` | 0.0 | 0.0 | отправной хаб |
| `X` | 0.5 | 0.0 | отклонение маршрута |
| `B` | 1.0 | 0.0 | хаб версии 1 и фактического отклонения |
| `D` | 1.5 | 0.0 | хаб версии 2 |
| `C` | 2.0 | 0.0 | конечный хаб |

#### Версии плана `R1`

| Версия | Период действия | План | SLA |
|---|---|---|---:|
| `R1-V1` | `[2025-01-01T00:00Z, 2025-02-01T00:00Z)` | `A → B → C` | 48 часов |
| `R1-V2` | `[2025-02-01T00:00Z, ∞)` | `A → D → C` | 36 часов |

Обе версии имеют плановую длину, равную двум градусам дуги экватора. Это не фиксированное число метров в спецификации; проверяется отношение вычисленных дистанций.

#### Посылки

| Package | Shipment | Сценарий | Ключевые события и ожидания |
|---|---|---|---|
| `P1` | `S1` | Нормальная доставка по старой версии | `picked_up=2025-01-10T08:00Z`, хаб `B` с `08:00→12:00`, `delivered=2025-01-12T08:00Z`. Использует `R1-V1`; срок 48 ч; обещанный срок совпадает с доставкой; on-time; dwell `B` = 4 ч; фактическая и плановая дистанции равны. |
| `P2` | `S2` | Опоздание и пространственное отклонение | `picked_up=2025-02-10T08:00Z`; посещения `B` 4 ч, `X` 10 ч, `D` 2 ч; `delivered=2025-02-12T08:00Z`. Использует `R1-V2`; срок 48 ч при SLA 36 ч; опоздание 12 ч; маршрут `A → B → X → D → C` имеет длину 150% плана; отклонение +50%; суммарный dwell = 16 ч, максимум в `X`. |
| `P3` | `S2` | Точный дубль и поздние события | `picked_up=2025-02-10T09:00Z`, `delivered=2025-02-11T21:00Z`; позднее загружаются завершённые посещения `B` 2 ч и `X` 1 ч с бизнес-временем до доставки, а также точный дубль события `picked_up`. После второй загрузки текущее состояние остаётся `delivered`, срок и on-time не меняются, canonical event count не увеличивается из-за дубля, маршрут становится `A → B → X → C` и равен 150% плана. |
| `P4` | `S3` | Незавершённая доставка | `picked_up=2025-02-12T08:00Z`, затем `arrived_at_hub D=2025-02-12T20:00Z`, отправления и доставки нет. Использует `R1-V2`; существует одна Gold-строка; текущее состояние `arrived_at_hub`; посещение `D` открыто с `dwell_time=NULL`; `delivered_at`, итоговый срок, опоздание, `is_on_time` и финальное отклонение маршрута равны `NULL`; дистанция до текущей точки рассчитана. |

`P2` и `P3` принадлежат одному shipment `S2` и должны сохранять независимые состояния и метрики.

#### Отрицательные DQ-сценарии

Они не входят в успешный baseline-run и выполняются отдельно:

- одинаковый `event_id` с различающимся payload должен провалить DQ-проверку;
- `departed_at_hub` без открытого `arrived_at_hub` должен провалить DQ-проверку;
- второе `arrived_at_hub` для той же посылки и хаба до закрытия текущего посещения должно провалить DQ-проверку.

### Делегировано или отложено

- Полный физический формат fixture-файлов, имена полей сверх согласованного контракта и структура каталогов выбираются агентом при реализации.
- События с разными `event_id` считаются разными событиями; невозможная последовательность выявляется DQ-тестами. Более сложная semantic deduplication не входит в первый срез.
- Gold первого среза ограничен accumulating package fact, hub-visit fact и агрегатом эффективности по версии маршрута.
- Поздно обнаруженная ретроактивная корректировка плана маршрута не входит в первый срез и должна быть определена перед соответствующим расширением.
- Точные сценарии schema evolution, time travel, partitioning benchmark и maintenance определяются перед последующими срезами; они не отменены.

## 6. Критерии приёмки

AC-001 и AC-002 следуют из исходника. AC-003–AC-012 являются обязательными критериями первого среза.

### AC-001 — соблюдение границ проекта

- **Исходные условия:** определён реализуемый учебный срез.
- **Действие:** сопоставить его состав с разделом Scope.
- **Ожидаемый результат:** срез использует заданный lakehouse-стек и deterministic fixtures; не включает ingestion/CDC/orchestration и другие явно исключённые технологии или направления.
- **Способ проверки:** ревью состава артефактов и зависимостей будущего проекта.
- **Основание:** `docs/idea.md`, разделы «Назначение», «Входит в scope», «Не входит в scope».

### AC-002 — покрытие учебных результатов

- **Исходные условия:** полный scope проекта завершён.
- **Действие:** пройти предусмотренные модели, тесты, запросы и maintenance exercises.
- **Ожидаемый результат:** каждый навык из раздела «Приобретаемые компетенции» представлен проверяемым заданием или результатом.
- **Способ проверки:** трассировка компетенций к отдельным критериям и артефактам; конкретная матрица будет сформирована после детализации срезов.
- **Основание:** `docs/idea.md`, «Приобретаемые компетенции».

### AC-003 — SCD2-версия плана маршрута

- **Вход:** планы `R1-V1`, `R1-V2` и посылки `P1`–`P4` из fixture package.
- **Действие:** построить SCD2-измерение и accumulating snapshot.
- **Ожидаемый результат:** `P1` связан ровно с `R1-V1`; `P2`, `P3`, `P4` — ровно с `R1-V2`; интервалы версий не пересекаются; `promised_delivery_at` вычислен из SLA связанной версии.
- **Способ проверки:** dbt relationship/uniqueness tests и запрос с ожидаемым mapping.
- **Основание:** DEC-017, DEC-023.

### AC-004 — Bronze и канонизация дублей

- **Вход:** обе партии событий `P3`, включая точный повтор `picked_up` с тем же `event_id`.
- **Действие:** загрузить обе партии и перестроить Silver.
- **Ожидаемый результат:** Bronze содержит обе исходные строки повтора; канонический Silver содержит одну запись этого `event_id`; остальные поздние события сохранены.
- **Способ проверки:** reconciliation counts по `event_id`, batch и слою.
- **Основание:** DEC-016.

### AC-005 — поздние события

- **Вход:** `P3`, у которой посещения `B` и `X` поступают после события `delivered`, но имеют более раннее `event_at`.
- **Действие:** обработать вторую партию.
- **Ожидаемый результат:** текущее состояние остаётся `delivered`; появляются hub visits `B=2 ч` и `X=1 ч`; срок доставки и on-time не меняются; фактическая дистанция пересчитывается с 100% до 150% плановой.
- **Способ проверки:** сравнение Silver/Gold до и после второй партии.
- **Основание:** DEC-016, DEC-022.

### AC-006 — итоговые метрики нормальной доставки

- **Вход:** `P1`.
- **Действие:** построить Gold.
- **Ожидаемый результат:** duration = 48 ч; delay = 0; `is_on_time=true`; dwell `B` = 4 ч; actual/planned distance = 100%; deviation = 0%.
- **Способ проверки:** dbt data test с фиксированным expected row.
- **Основание:** DEC-011–DEC-015, DEC-023.

### AC-007 — опоздание, хабы и отклонение маршрута

- **Вход:** `P2`.
- **Действие:** построить Gold.
- **Ожидаемый результат:** duration = 48 ч; `promised_delivery_at=2025-02-11T20:00Z`; delay = 12 ч; `is_on_time=false`; hub dwell: `B=4 ч`, `X=10 ч`, `D=2 ч`; суммарный dwell = 16 ч; actual/planned distance = 150%; deviation = 50%.
- **Способ проверки:** dbt data tests и reconciliation между package, hub visit и route metrics.
- **Основание:** DEC-011–DEC-015, DEC-022, DEC-023.

### AC-008 — accumulating snapshot незавершённой доставки

- **Вход:** `P4`.
- **Действие:** построить Gold до получения дальнейших событий.
- **Ожидаемый результат:** существует ровно одна строка `P4`; current status = `arrived_at_hub`; посещение `D` открыто и имеет `dwell_time=NULL`; `delivered_at`, duration, delay, `is_on_time` и финальное distance deviation равны `NULL`; дистанция до текущей точки не `NULL`.
- **Способ проверки:** dbt data test с expected null/non-null contract.
- **Основание:** DEC-021, DEC-022.

### AC-009 — негативные проверки качества

- **Вход:** каждый отрицательный DQ-сценарий запускается отдельно.
- **Действие:** выполнить соответствующие dbt tests.
- **Ожидаемый результат:** conflicting payload для одного `event_id`, departure без arrival и повторный arrival до departure приводят к провалу предназначенного для них теста; baseline fixtures проходят эти тесты.
- **Способ проверки:** ожидаемый exit status тестового запуска и имя упавшего теста.
- **Основание:** DEC-016, DEC-022.

### AC-010 — агрегаты эффективности маршрута и хабов

- **Вход:** согласованный baseline после обеих партий событий.
- **Действие:** построить агрегат по версии маршрута и агрегаты завершённых посещений хабов.
- **Ожидаемый результат:** для `R1-V1` completed packages = 1, on-time rate = 100%, average delay = 0, average final route deviation = 0%; для `R1-V2` completed packages = 2, active packages = 1, on-time rate среди завершённых = 50%, average delay среди завершённых = 6 ч, average final route deviation = 50%. Завершённый dwell: `B=6 ч`, `X=11 ч`, `D=2 ч`; открытое посещение `P4/D` не включается в сумму завершённого dwell.
- **Способ проверки:** dbt data tests с фиксированными expected aggregates.
- **Основание:** DEC-013, DEC-021, DEC-026.

### AC-011 — reconciliation между слоями

- **Вход:** согласованный baseline после обеих партий событий.
- **Действие:** сопоставить Bronze, canonical Silver и Gold.
- **Ожидаемый результат:** Bronze сохраняет все исходные строки; разница с canonical Silver объясняется только точными дублями `event_id`; package fact содержит 4 строки, из них 3 завершённые и 1 активную; hub-visit fact содержит 7 посещений, из них 6 закрытых и 1 открытое; shipment `S2` содержит две независимые package-строки.
- **Способ проверки:** custom reconciliation tests.
- **Основание:** DEC-009, DEC-016, DEC-021, DEC-022, DEC-025.

### AC-012 — сквозная работа lakehouse-стека

- **Исходные условия:** выбранные версии компонентов закреплены, Polaris и S3-compatible storage настроены.
- **Действие:** через Trino Iceberg connector и REST catalog создать/записать таблицы первого среза, затем выполнить dbt build и прочитать Gold-результаты.
- **Ожидаемый результат:** таблицы зарегистрированы в Polaris, их data/metadata files размещены в object storage, Trino читает результаты, а обязательные baseline dbt tests проходят.
- **Способ проверки:** catalog listing, запросы Trino, проверка object-storage paths и успешный `dbt build`; это план проверки, а не уже выполненный результат.
- **Основание:** `docs/idea.md`, DEC-005, DEC-018, DEC-027.

## 7. Первый законченный срез

### Решено пользователем: core vertical slice

Первый срез включает:

- рабочую цепочку S3-compatible storage → Polaris → Iceberg → Trino → dbt;
- deterministic fixture batches для tracking-событий и версий плана маршрута;
- immutable Bronze;
- Silver с каноническими событиями и текущим состоянием посылки;
- SCD2-измерение плана маршрута с join по `picked_up_at`;
- Gold-результаты по SLA доставки, времени в хабах и отклонению фактического маршрута;
- dbt tests и reconciliation для ключевых контрактов данных.

В последующие срезы отложены, но остаются обязательной частью полного scope:

- schema evolution;
- отдельное упражнение time travel;
- partitioning benchmark и анализ `EXPLAIN`/file pruning;
- small-files diagnostics;
- snapshot expiration и compaction.

- Apache Polaris: официальный Trino guide документирует REST endpoint `/api/catalog`, warehouse/catalog name, OAuth2 и S3-compatible endpoint/path-style configuration. Источник: Apache Polaris repository documentation, Context7 `/apache/polaris`.

## 9. Передача состояния

### Согласовано источником

- назначение и учебная направленность проекта;
- основной технологический стек;
- deterministic fixtures вместо ingestion/CDC;
- верхнеуровневый Bronze/Silver/Gold и Kimball scope;
- перечень компетенций;
- явные исключения.

### Решено пользователем

- единый домен — логистика;
- главный аналитический результат — анализ сроков доставки и эффективности маршрутов;
- основная единица учёта — посылка (`package_id`);
- одно отправление может включать несколько посылок, доставляемых независимо;
- жизненный цикл представлен неизменяемыми tracking-событиями;
- Bronze хранит полную историю событий, Silver вычисляет текущее typed state;
- срок доставки и SLA оцениваются по варианту 1;
- маршрут дополнительно оценивается сравнением планового и фактического расстояния или участков по варианту 3;
- используется анализ времени ожидания в хабах по варианту 2;
- все три вида анализа входят в scope;
- плановый и фактический маршруты представлены координатами хабов и tracking-событий, а расстояния вычисляются из этих координат;
- фактическая дистанция использует все координатные tracking-события, упорядоченные по бизнес-времени, и суммирует расстояния между соседними точками;
- Bronze сохраняет все строки, Silver канонизирует события по `event_id`, принимает поздние события и использует детерминированный порядок `(event_at, received_at, event_id)`;
- SCD2 применяется к плану маршрута, а факт доставки использует версию, действовавшую на `picked_up_at`;
- первый законченный срез — core vertical slice со всеми тремя видами аналитики и тестами;
- schema evolution, time travel, partitioning benchmark и maintenance отложены на последующие срезы, но остаются в полном scope;
- после одобрения агент реализует весь scope и принимает обратимые технические решения, не изменяющие бизнес-результат;
- для геодезического расстояния принято использование Trino `ST_Distance` над `SphericalGeography`; документация проверена, выполнение не проверялось;
- Gold-факт доставки — accumulating snapshot с одной строкой на посылку; у незавершённой доставки финальные метрики равны `NULL`;
- посещения хаба формируются строгим pairing и получают `visit_seq`; некорректные последовательности считаются ошибкой качества;
- `promised_delivery_at` вычисляется из SLA SCD2-версии маршрута, действующей на `picked_up_at`.

- deterministic fixture package `P1`–`P4` с нормальной, опоздавшей, поздно дополненной и незавершённой доставкой;
